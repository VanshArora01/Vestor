# PROJECT_CONTEXT.md — Vestor

**This document is the single source of truth for Vestor.** Every implementation task — feature design, API design, prompt design, UI design — must be checked against this document before work begins. Do not invent features outside this document. Do not rename modules or bypass the architecture below without updating this document first.

---

## 1. Product overview

Vestor is an AI-powered financial literacy and investment platform. It is not an expense tracker, not a portfolio tracker, not a chatbot, and not a course — it is a single financial ecosystem where every module reads from and writes to one shared user financial profile.

Tagline: **Learn. Manage. Invest.**

---

## 2. Vision

A user should be able to go from not understanding personal finance to actively and correctly managing their money, investments, and long-term goals — inside one product, without needing to leave it for a course, a spreadsheet, or a separate broker app to understand what they're doing.

## 3. Mission

Turn financial knowledge into financial action, immediately, using the user's own real numbers — never generic advice, never content in isolation from their actual financial life.

---

## 4. Core philosophy: Learn → Apply → Improve

No module teaches without a path to action, and no action happens without the user's own data informing it.

```
User learns a concept (Academy)
        ↓
AI grounds the concept in the user's real numbers (Financial Context Service)
        ↓
AI proposes a concrete action (goal, budget change, reallocation)
        ↓
User confirms — nothing is created or changed without explicit user action
        ↓
Dashboard reflects the change immediately
```

This loop is Vestor's core differentiator. Every new feature must be checked against it: does this feature close the loop, or does it just add content/data in isolation?

---

## 5. Product principles

1. **One profile, one truth.** Every module reads and writes the same underlying financial data. No module maintains its own private copy of a concept another module owns (see Non-negotiable Rules, #2).
2. **AI proposes, the user decides.** AI never writes to the user's financial data without explicit confirmation.
3. **Every module must justify its AI usage.** AI exists to make a specific module's core action better — not as a bolted-on chatbot feature.
4. **Consistency over novelty.** A production SaaS product doesn't have one module that looks like a mobile game and six that look like a fintech dashboard. Pick one visual language and hold it everywhere.
5. **Reusable services over duplicated logic.** If two modules need the same computation (aggregation, AI reasoning, retrieval), it lives in one shared service, not two implementations.

---

## 6. Target users

Primary: Indian students and early-career professionals who have income but little structured financial knowledge — the gap between "earning money" and "knowing what to do with it."

Secondary: users already investing casually (stocks/mutual funds) who want their learning, budgeting, and portfolio in one place instead of scattered across apps.

---

## 7. Brand identity

- **Name**: Vestor
- **Tagline**: Learn. Manage. Invest.
- **Visual language**: minimal, professional, modern, premium — the product should read as a production fintech SaaS tool, not a hackathon demo or a gamified learning app skinned onto a dashboard.
- **Tone**: direct, clear, non-condescending — financial content written for someone who doesn't know the concept yet, without talking down to them.

## 8. Core modules

Each module owns its own data and UI. None of them own AI logic or cross-module aggregation directly — those are shared services (see Section 10).

### 8.1 Dashboard
Central overview. Answers "how am I doing financially?" Reads from the Financial Context Service — computes nothing itself.

### 8.2 Finance
Manual income, expenses, budget, debt, and loan tracking. Emergency Fund is **not** a separate entity here — it reads/writes to the Emergency Fund goal owned by Goals (Section 10, single-entity rule). AI-driven spending insights are requested from the AI Orchestration Layer, not computed locally.

### 8.3 Goals
Target-based tracking (amount, deadline, progress, contribution history), including Emergency Fund as a first-class goal type. Source of truth for all goal data platform-wide.

### 8.4 Academy
Gamified, personalized learning path. Lessons are generated by the AI Orchestration Layer using curated curriculum content + the user's live Financial Context. Every lesson ends in a proposed action (create/update a goal, adjust a budget) that the user confirms — closing the Learn → Apply → Improve loop. Gamification is limited to XP, badges, streaks, and progress — no illustrative path animations (see Non-negotiable Rules, #5).

### 8.5 Portfolio
Manual investment entry (stocks, mutual funds, ETFs, gold, FD, PPF, NPS). Computes value/gain-loss/allocation locally (this is portfolio-specific math, not shared aggregation). Diversification/risk commentary is requested from the AI Orchestration Layer.

### 8.6 Market
Simplified news and economic calendar. Does not directly query Portfolio data — "what does this news mean for my portfolio" is answered by the AI Orchestration Layer, which pulls both Market content and the user's Financial Context as needed. This keeps Market and Portfolio decoupled.

### 8.7 Advisor
Conversational AI assistant with full Financial Context access (Finance, Goals, Portfolio, Academy progress). Calls the same AI Orchestration Layer every other module uses — Advisor is a UI surface for that layer with conversational framing, not a separate AI system. The future "Financial Decision Engine" only ever proposes plans; it never executes a transaction, goal creation, or reallocation without explicit user confirmation.

---

## 9. AI philosophy

- AI enhances every module; it does not replace the application logic of any module.
- Every AI response must be relevant, actionable, personalized, and context-aware — grounded in the user's actual data, not generic.
- AI never writes to user financial data without explicit user confirmation. No exceptions, including in Advisor's decision engine.
- All AI logic — prompt construction, retrieval, model calls — lives in one shared **AI Orchestration Layer** (Section 10). No module implements its own prompt logic or its own LLM calls.

---

## 10. Architecture — shared services

This is the layer that was missing from the original module list, and it's what prevents five modules from each rebuilding the same logic.

```
┌─────────────────────────────────────────────┐
│  Presentation (React + TS + Tailwind)         │
│  Dashboard · Finance · Goals · Academy ·      │
│  Portfolio · Market · Advisor                 │
└───────────────┬───────────────────────────────┘
                │
┌───────────────▼───────────────────────────────┐
│  Financial Context Service                    │
│  Single source of aggregated user data:        │
│  income, expenses, net worth, goal progress,   │
│  portfolio value, learning progress            │
└───────────────┬───────────────────────────────┘
                │
┌───────────────▼───────────────────────────────┐
│  AI Orchestration Layer                        │
│  Prompt templates · RAG retrieval (Qdrant) ·    │
│  Gemini API calls · response formatting         │
│  Used by: Academy, Advisor, Portfolio insights, │
│  Finance insights, Market summaries             │
└─────────────────────────────────────────────────┘
```

Module-specific computation (e.g. Portfolio's gain/loss math, Goals' progress percentage) stays inside that module — only the *cross-module* aggregation and *all* AI logic are centralized.

## 12. Development philosophy

- Architecture before implementation. Every feature defines purpose, user flow, UI, backend, database, and AI logic before code is written.
- No duplicate business logic — if two modules need the same thing, build the shared service, don't copy the logic.
- Clean, reusable services over module-specific one-offs.
- Build order should always produce a working, demoable product at the end of every phase — never a half-integrated big-bang merge at the end.

---

## 13. Non-negotiable rules

1. **AI proposes, the user decides.** No AI-initiated write to financial data, ever — not in Academy, not in Advisor, not in the future Decision Engine.
2. **One entity, one owner.** Emergency Fund lives in Goals. Financial aggregates live in the Financial Context Service. No module maintains a private duplicate of data another module owns.
3. **One AI Orchestration Layer.** No module implements its own prompt logic, its own retrieval, or its own model calls.
4. **No cross-module hard dependencies.** Market does not query Portfolio directly, Academy does not query Portfolio directly — all cross-module context flows through the Financial Context Service or the AI Orchestration Layer.
5. **Visual consistency.** Gamification in Academy is limited to XP, badges, streaks, and progress indicators — no path-style illustrative animation. The product's visual language is minimal/professional/premium everywhere, including Academy.
6. **Do not invent modules or rename existing ones without updating this document first.**
